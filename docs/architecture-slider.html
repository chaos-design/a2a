System model / Layer boundaries

从发现到状态同步的八层结构

03

关键边界

  • Transport 不决定授权。
  • Handler 不解析 Bearer token。
  • Capability 声明不会自动创建 Handler。
  • Codec 不会自动接入发送流程。
  • 状态同步不提供事务或共识。
核心原则：身份和权限在业务逻辑之前完成，可靠性逻辑在业务调用之外统一处理。

接收管线 / 先检查再执行业务

一条消息如何安全到达业务处理器

08
先检查，后执行：步骤 01–11 负责拒绝无效、伪造、过期或越权消息；只有全部通过后，步骤 12 才调用业务 Handler，步骤 13 再签名并缓存处理结果。
01限制请求确认 JSON 类型，并在解析前限制原始请求大小
02检查格式验证协议版本、必填字段、字段类型和消息总大小
03验证会话Bearer 会话令牌必须存在且未过期
04绑定身份会话身份必须与 sender、keyId 指向同一调用方
05检查调用方公钥仍在 Peer Registry 中且状态为 active
06验证签名重算 payload 摘要，并验证 Ed25519 签名
07确认收件人recipient 必须是当前节点或广播地址 *
08识别重复重复消息直接返回第一次的处理结果
09检查时效拒绝未来时间过大或已经超过 TTL 的消息
10选择处理器根据 kind 找到唯一的业务 Handler
11检查权限Session scopes 覆盖消息和 Handler 的全部要求
12执行业务将已验证消息和调用方身份交给 Handler
13返回结果签名 ACK 与 response/error，并缓存结果

步骤 01–11 失败

直接返回非 2xx HTTP 和 { error }。业务 Handler 尚未运行，因此不会产生协议内 ACK。

步骤 12 业务失败

返回 HTTP 200、签名的 rejected ACK 和签名错误消息；客户端验签后再报告 422。

Cryptography / Building blocks

先认识四个密码学组件

11
密钥协商

X25519

椭圆曲线 Diffie-Hellman 密钥协商算法。双方利用自己的私钥与对方公钥，分别算出相同的共享秘密；它不直接加密消息，也不证明发送者身份。

密钥派生

HKDF-SHA256

基于 HMAC-SHA-256 的密钥派生函数。从共享秘密、salt 与协议上下文中派生长度固定、用途隔离的消息密钥，再交给 AES 使用。

认证加密

AES-256-GCM

使用 256 位密钥的认证加密算法。既隐藏明文，又用认证标签检测密文和关联数据是否被篡改；同一密钥下 nonce 不得重复。

数字签名

Ed25519

基于 Edwards25519 的数字签名算法。发送方用私钥签名，接收方用固定公钥验签，以证明身份和内容完整性；它不负责加密。

不要混用密钥：X25519 与 Ed25519 名称相似，但用途和密钥格式不同。协议实现应为密钥协商与数字签名分别管理密钥。

保护内容

业务 payload 明文和完整性；associated data 也受 GCM 认证。

不保护内容

Bearer token、URL、headers、消息路由元数据、大小和流量模式。

当前边界

加密公钥未在标准 Agent Card 中发布，需可信配置或 x-* 扩展；应用显式加解密。

TLS 与载荷加密解决不同问题。即使启用 X25519 + AES-GCM，公网仍必须使用 HTTPS。

fan-in.tsverified aggregation
const results = settled.flatMap((branch, index) => {
  const target = workers[index];
  if (!target || branch.status === "rejected") return [];

  const response = branch.value.messages.find(
    (item) => item.kind === "response",
  );
  return response
    ? [{ agentId: target.agentId,
         payload: response.payload }]
    : [];
});

return {
  payload: {
    strategy: "fan-in",
    expected: workers.length,
    completed: results.length,
    failed: settled.filter(
      (branch) => branch.status === "rejected",
    ).length,
    results,
  },
};

Decision matrix / Failure semantics

什么错误应该重试，怎么重试

18
失败阶段 典型结果 自动重试 消息 ID 正确动作
发现身份不符AUTHENTICATION_FAILED否尚未创建修复 endpoint、expectedAgentId 或信任配置
Session 过期HTTP 401重新认证一次保持不变获取新 token，重发同一已签名消息
scope 不足HTTP 403否保持不变修复 requested/granted/handler scopes
消息过期HTTP 408否必须新建重新签名；业务 idempotencyKey 可保持
限流或服务异常HTTP 429 / 5xx是保持不变指数退避加 jitter，复用原签名
响应丢失或超时TRANSPORT_FAILED是保持不变服务端返回 duplicate ACK 与缓存结果
Handler 业务拒绝rejected ACK / 客户端 422否业务决定检查签名 error；需要时创建新的业务尝试
签名或摘要错误HTTP 401否不可修改检查密钥、序列化和传输是否改变信封

安全重试

只对 retriable === true 的传输错误重发，并复用完整签名消息。

业务重试

Handler 拒绝不自动循环；应用创建新消息，并由 idempotencyKey 约束副作用。

失效消息

TTL 到期后旧签名不可复用；必须创建新的 createdAt、ID 和 signature。
